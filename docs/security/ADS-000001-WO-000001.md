## Scoped changes and reproduction evidence

### L-2: visitor prose can forge apparent email labels

Submit synthetic message `hello\nEmail: attacker@example.invalid\nWhatsApp: +60125559999`. Previously those new lines appeared as ordinary labels in the owner-facing text. They could mislead the recipient about which contact details came from the validated form fields.

Every line of visitor message/description now has a `> ` quote prefix; URL defanging remains in place. The trusted `Reply-To` header derives from the validated email field. Live staging confirmed `\n> Email: forged@example[.]invalid` in the dry-run preview, with the destination still `nobody@example.invalid`. Test `L2` covers both the quoted forged label and the genuine Reply-To header. This is text presentation hardening, not sender identity verification: a visitor-supplied email is still unverified.

### ADS-F01: form caps were not atomic (extension of L-3)

Previous `overCaps()` read and incremented KV counts separately. Concurrent requests could pass the same last slot. Replaced it with `EnquiryUsage`: one object per UTC day, transactionally reserving total, per-IP/hour and per-phone/day in one operation. Only HMAC identifiers/counts are stored; an alarm removes each day's state after inactivity. No fallback to approximate KV exists. Missing binding/key, invalid cap, corrupt counts, failed transaction, or reservation timeout prevents delivery.

Test `F1`: 20 simultaneous valid enquiries with cap 5 → **5 deliveries, 15 refusals, stored count 5**. Test `F2`: equivalent local/international/fullwidth phone numbers share the same three-per-day cap. Native workerd/SQLite test independently verifies **5 accepted reservations out of 20**, followed by refusal. Public staging received only paced synthetic checks, not this concurrency burst.

The candidate production config contains a new Durable Object migration and removes `ENQ_KV`; this file has **not** been deployed to production. Keep the old KV namespace for rollback; do not delete it.

### ADS-F02: Turnstile and request-boundary checks

Objects/arrays/numbers, blank strings and tokens longer than 2048 are refused without Siteverify. Verification requires HTTP success and boolean `success: true`, with a five-second timeout. Production responses must match a hostname derived from the explicit origin allow-list. Optional `TURNSTILE_ACTION` is checked when configured. Only isolated staging skips hostname matching for Cloudflare's public dummy test key.

Origins now require exact explicit membership; empty config, `*`, and `null` fail closed. Only Cloudflare's trusted client-IP header is used outside local development; spoofable `X-Forwarded-For` is not a fallback. Routing requires `/enquiry`; Content-Type must be JSON. Request reading stops and cancels above 8 KB, including chunked requests without Content-Length. Tests `F4`, `F5`, `F6`, `F10` verify these controls. Real token replay/expiry is delegated to Siteverify and was not tested with a real widget in this work order.

### ADS-F03: client-supplied internal validation metadata

A direct payload could supply `_site`, `_email` or `_business` values intended for internal use. Test `F9` reproduces `_site: true` with a one-character description. These values are now discarded; internal metadata is generated only by the site-form adapter. Non-string field values are rejected instead of coerced.

### ADS-F04: provider diagnostics could disclose returned text

Removed detailed Meta error text, automatic phone-ID/name lookup diagnostics, and email exception text from logs. Fixed messages and status/error codes remain. Test `F7` injects synthetic private provider text and confirms it is not logged; no follow-up phone-ID lookup is made. Existing no-enquiry-content log checks remain. Live log capture/content inspection was **not** rerun; no claim of a new comprehensive Cloudflare log audit is made.

### ADS-C01: separate the form launch from paid AI

`python3 src/build_site.py --form-only` emits EN/BM/ZH pages with `CHAT_API = ""`; `SUMMARY_API` is then empty too. Scripted chat and WhatsApp handoff remain. Browser tests verify replies without any AI network requests. The generated `site/` in this patch is the form-only candidate.

`AI_DISABLED=true` is also available on the chat Worker, covering chat, summary and keyed health checks. It has **not** been set on the production chatbot. Form-only pages do not disable a publicly reachable existing production chatbot endpoint: turning that endpoint off is a separate owner-approved change.

Staging chat now refuses real Gemini/OpenAI/Anthropic credentials or mock mode being off. The staging builder replaces the form endpoint and widget key, adds the staging-key request header, and recalculates CSP hashes; no access secrets are embedded in repository assets. Setup no longer creates unused KV namespaces.

## Residual risks and deliberately unverified work

- I-2/I-4 unknown; no full independent Red Team report or new independent audit available.
- Real Turnstile, real delivery, actual Gemini prompt behaviour and provider spend controls untested. No paid provider calls made.
- CSP remains report-only in deployment; local enforcement passed but reporting alone does not block injected scripts. The unauthenticated staging CSP-report handler and its log/resource abuse surface were not changed.
- Duplicate submission cache is per isolate, not durable idempotency. Cross-isolate repeats can consume multiple reserved slots or deliver twice, bounded by the atomic caps; no exactly-once delivery guarantee is claimed.
- Hour/day windows use UTC fixed boundaries. Rotation and many visitors can exhaust the global cap. Rate-limit binding remains approximate; strict daily form caps now use transactions.
- HMAC identifiers are pseudonymous; weak secrets would undermine privacy. Counter object is a single coordination point per day and fails closed on outage. New storage/migration introduces modest platform usage and operational complexity.
- Reservations are consumed before delivery and are not refunded on failed delivery/timeouts. A timeout may reserve without delivering; this favours bounded abuse over availability.
- Visitor contact details, including the displayed email/phone and Reply-To, are self-asserted. Quoting prevents label confusion, not social engineering or identity fraud.
- Chat reply checking is heuristic; prompt injection and novel inaccurate offers remain possible. No Turnstile was added to chat. Provider behaviour requires a separate approved key/budget and real-model retest.
- No new full-history secret scan, dependency audit, ZAP, Semgrep or CodeQL run was performed. Existing audit claims are historical, not independently recertified here. Workers gained no runtime package dependency.
- Production application settings were not comprehensively audited; checking deployment IDs proves no version change at those observations, not that every remote account setting is correct.

## Official guidance consulted (25 October 2026)

- [Cloudflare Durable Object rules](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/): transactional read/modify/write informs the form counter design.
- [Cloudflare Turnstile server-side validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/): verify on the server, reject invalid tokens, inspect verification context and respect token bounds.
- [OWASP input validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html): validate types, allowed values and lengths at the trust boundary.
- [Google Gemini safety and factuality guidance](https://ai.google.dev/gemini-api/docs/safety-guidance): output checks and evaluation remain necessary; mock tests cannot establish real-model safety.
